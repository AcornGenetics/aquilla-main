# PRD — Phase A: Instrument Geometry & Well-Count Identity

**Status:** ready-for-agent
**Part of:** Mk II 15-Well migration (`specs/15-well-implementation-plan.md`, tracker `specs/15-well-mkii-migration.md`)
**Scope:** Phase A only (Days 1–2). The reactive refactor that consumes this (Phase B) and the motor/optics work (C–F) are separate PRDs.

---

## Problem Statement

The Sentri comes in two physical builds: the original 4-well instrument and the new Mk II 15-well instrument. Today the software has **no reliable, single way to know which build it is running on** — the well count is a scattered magic literal (`[1,2,3,4]`, `range(6)`) and the engineers' Mk II draft added surface `host_config.json` flags (`well_15`, `two_adcs`, `updated4`) that can drift, can express illegal states, and force `if well_15` branching through the codebase.

As the team, we need a device to **know its own [[Plate Geometry]]** (how many [[Well]]s it has and how they are arranged) from a single authoritative source that:
- is set once when the physical unit is built and does not drift,
- is not a casually-editable config file and is not regenerated by the deploy scripts,
- lets the existing 4-well fleet keep working untouched,
- and is the one input every geometry-dependent part of the code reads.

Without this, every downstream phase (motion, optics file, analysis) has nothing consistent to key off, and a 4-well and 15-well device cannot safely share one codebase and one fleet.

## Solution

Give each device a small, durable **identity record** that names its well count, and a single code path that turns that into a logical [[Plate Geometry]] the rest of the system reads.

From the team's perspective:
- When a unit is provisioned, the operator states its well count once (4 or 15). The Greengrass deploy script writes it into an immutable identity file that nothing later overwrites.
- On the device, one accessor reads that file and hands out the instrument's Plate Geometry (rows × columns and everything derived from it). Every geometry-dependent module asks that accessor — there is no scattered "4" and no mode flag.
- An existing 4-well unit with no identity file simply defaults to 4-well and keeps running.
- If the file is corrupt or names an unsupported well count, the device fails loud rather than guessing.

This Phase delivers **only the identity + geometry foundation** (the read side and the write side). It does not change motion, optics, or analysis — those consume the geometry in later phases.

## User Stories

1. As the team, I want a device to resolve its own well count from a single authoritative record, so that no part of the code has to hardcode "4".
2. As the team, I want the well count set once at provisioning, so that it reflects the physical build and cannot drift run-to-run.
3. As an operator provisioning a 15-well unit, I want to state "15 wells" once during the Greengrass deploy, so that the device is correctly configured from birth.
4. As an operator provisioning a 4-well unit, I want to state "4 wells" (or accept the default), so that the standard build is configured with no extra ceremony.
5. As an operator, I want the well count entered the same way the device hostname already is (prompt-if-unset), so that provisioning feels consistent with what I do today.
6. As the team, I want the identity record to be immutable after it is written, so that a stray script, an OTA update, or an accidental edit cannot change what the machine believes it is.
7. As the team, I want the identity record kept separate from `host_config.json` and `device.env`, so that the deploy scripts that regenerate those never touch the identity.
8. As an operator recovering a mis-provisioned bench unit, I want a single deliberate command to unlock and rewrite the identity, so that mistakes are correctable without special tooling.
9. As the existing 4-well fleet, I want a device with no identity file to default to 4-well, so that units that predate this feature keep working without being re-provisioned.
10. As the team, I want a device with a corrupt or unsupported identity file to fail loud, so that a genuine misconfiguration surfaces instead of silently running the wrong geometry.
11. As a developer, I want one accessor that returns the device's Plate Geometry, so that every geometry-dependent module reads the same source of truth.
12. As a developer, I want the Plate Geometry to be purely logical (rows, columns, sensor offset, channels, and everything derived), so that it carries no per-unit calibration and has no dependency on `host_config.json`.
13. As a developer, I want the well count to map to a canonical geometry through a registry, so that adding a future build is a single data entry with zero control-flow change.
14. As a developer, I want the registry to assert that each entry's derived well count matches its key, so that a mistyped geometry is caught at load rather than in the field.
15. As a developer, I want per-Well identities (e.g. `1A`–`5C`) derived from the geometry, so that downstream code refers to Wells by a stable, geometry-driven label.
16. As a developer, I want the scan order (the serpentine traversal for a 3×5, the single row for a 1×4) derived from the geometry, so that later phases consume it rather than reimplementing it.
17. As the team, I want the motor to keep reading its measured positions from `host_config.json` unchanged, so that per-unit calibration stays where it already lives and this Phase does not migrate calibration data.
18. As the team, I want the device to fail loud if `host_config.json`'s number of axis positions does not match the geometry, so that a 15-well unit with a 4-well hardware config is caught before the motor misbehaves.
19. As the team, I want the identity record to survive OTA updates and container swaps, so that a device does not forget its well count on a routine update.
20. As the team, I want a full SD reimage to require re-provisioning the well count, so that a wiped device is deliberately re-birthed rather than defaulting silently on new hardware.
21. As the team, I want the identity mechanism to be fully independent of the Device Certificate and `acorn-ca`, so that the enroll/renew path never has to know or carry the well count.
22. As a developer, I want the geometry accessor to cache its result, so that the many modules that read it do not each re-read the file.
23. As the team, I want the 4-well behavior to remain byte-identical after this Phase, so that introducing the geometry foundation does not regress the shipping product.

## Implementation Decisions

**Identity record (the durable, immutable file)**
- The record is a new file, distinct from `host_config.json` and `device.env`. It contains the **well count as an integer** (`4` or `15`), plus a schema version and a provisioned timestamp. The well count is the single human-set value.
- It is written by the **Greengrass deploy script**, host-side as root, **write-once**: guarded by an existence check, then made immutable (Linux immutable attribute) so regeneration, OTA, and accidental edits cannot alter it.
- The well count enters the deploy script the same way the device hostname does today — a prompt-if-unset with a default of **4**. Garbage input is rejected at write time (must be a supported count).
- Recovery is a deliberate two-step: clear the immutable attribute, remove/rewrite, re-provision.
- The record lives on the persistent config volume so it survives OTA and container swaps; a full SD reimage wipes it (re-provision required). The deploy script must not bulk-delete the config directory (an immutable file would error).
- Explicitly **not** bound into the Device Certificate — no `acorn-ca` coupling. (OTP fuses and cert-binding were both considered and rejected: OTP is permanently unrecoverable during bring-up; cert-binding couples identity to the enroll path.)

**Plate Geometry (purely logical) + registry**
- Introduce a `PlateGeometry` value object that is **purely logical**: rows, columns, the FAM/ROX sensor offset, and channels; with **well count, per-Well ids, and scan order derived**. It holds **no measured motor steps**.
- Introduce a registry keyed by **well count** that maps `4 → 1×4` and `15 → 3×5`. Adding a build is one registry entry. A load-time invariant asserts each entry's derived well count equals its key. Assumption: **one canonical layout per well count** (revisit only if a same-count/different-layout build ever appears).

**Geometry accessor (the single read path)**
- Introduce one accessor that reads only the identity file, validates the well count against the registry, caches, and returns the `PlateGeometry`.
- Behavior: **absent file → default to 4-well (with a logged warning)**; **malformed file or unsupported well count → fail loud (raise/halt+log)**. Absent is treated as "legacy 4-well," corrupt is treated as an error.
- The accessor reads **nothing** from `host_config.json`.

**Motor / host_config boundary**
- The motor continues to read its **measured positions from `host_config.json` unchanged** — no calibration is moved in this Phase.
- Add a **consistency check** invoked where the motor loads: the number of axis positions in `host_config.json` must equal the geometry's columns plus the sensor offset; a mismatch fails loud.

**Naming**
- The accessor is named for what it does (return the geometry), not "detect" — there is no hardware detection in Phase A.
- Per-Well labels are column-then-row (`1A`–`5C`), matching the operator-facing convention; this is the canonical scheme (reconcile any internal row-then-column shorthand to it).

## Testing Decisions

**What makes a good test here:** exercise external behavior through the highest public seam — the registry/`PlateGeometry` derived outputs, the geometry accessor's observable results for each input condition, and the consistency check's pass/fail — never internal representation. Point the identity-file location at a temporary file to drive the accessor; do not mock internals.

**Modules under test**
- **Registry + `PlateGeometry` (pure logic):** assert derived outputs for both builds — well count, per-Well ids (`1A`–`5C`), the serpentine scan order for 3×5 and the single-row order for 1×4, the sensor offset — and the registry's `well_count == key` invariant. *Prior art:* `tests/unit/test_optics_read_plan.py` (asserts a geometry/plan structure's derived values).
- **Geometry accessor (file read + validation):** with a temp identity file, assert: valid `15` → 3×5; valid `4` → 1×4; **absent → default 4 with a warning**; **malformed JSON → raises**; **unsupported count (e.g. `5`) → raises**. Caching is observable via a single returned identity across calls.
- **Consistency check (pure helper):** a matching position count passes; a mismatch raises. *Prior art:* the assertion style in the existing unit suite; `tests/unit/hardware/test_motor.py` for the motor boundary (hardware-marked where it must touch hardware).
- **Deploy-script write:** reuse the deploy script's own inline `run_test` self-check harness — after writing, assert the identity file exists, is valid JSON, names a supported well count, and carries the immutable attribute. Bash is not unit-tested with a new rig; full write→read is a bench/integration check.

**Placement:** pure-logic and accessor tests go in `tests/unit/` (alongside `test_optics_read_plan.py`); the deploy self-checks live in the deploy script itself. Any test that must drive real hardware is marked accordingly and documented as not runnable in CI.

## Out of Scope

- The **reactive refactor** that removes the scattered literals and mode flags and makes the code consume `PlateGeometry` (Phase B).
- All **motion** work: the serpentine drive, real 5-well axis calibration, the pigpio deployment change (Phase C).
- The **optics file** writer/format and the **parser** (Phases D–E).
- **Analysis**, control-aware QC, and the `run_complete` event scaling (Phase F).
- **GUI** (Phase G).
- Any **hardware-based** identity detection (ADC-ID probe, homing-travel classification) — explicitly removed; the well count is a trusted provisioned flag.
- Moving motor calibration out of `host_config.json` — it stays where it is.
- Cryptographic/OTP tamper-resistance of the identity record — considered and deferred; the immutable file is the chosen mechanism.

## Further Notes

- **Accepted trade:** with no hardware cross-check, a *valid-but-wrong* well count (e.g. a unit provisioned `15` that is physically 4-well) is not caught by software; the motor will drive to positions that do not exist on the first run. The backstop is careful once-at-build provisioning plus one-command re-provision. This was a deliberate decision to drop the hardware/calibration dependency.
- **Guardrails carried from the migration plan:** (1) everything derives from one `PlateGeometry` — no hardcoded counts, no `if well_15` / `elif` mode branches, no int-vs-tuple type-sniffing; (2) 4-well never regresses — the 4-well build is the degenerate single-row case of the same code path, verified byte-identical.
- **Glossary:** `CONTEXT.md` has been updated — [[Well]] is no longer fixed at 4, and [[Plate Geometry]] is defined as the `rows × columns` arrangement that is the single source of truth for well count and layout.
- **ADR candidate:** the identity mechanism (immutable well-count file, chosen over OTP permanence and over certificate-binding) is hard-to-reverse and trade-off-driven — worth an ADR when this lands.
- **Downstream dependency:** Phase B and everything after consume `geometry()` and the derived scan order; freezing this accessor's shape early unblocks them.
